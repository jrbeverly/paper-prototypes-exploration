Prototypes as questions

The assumption: A prototype is an early, incomplete version of the final product.

The question: What if a prototype is not an implementation at all — but a question posed in code?

Every prototype should answer a question.

This reframes what it means to build something exploratory. A prototype is not a rough draft of the software you intend to ship. It is an experiment designed to reduce uncertainty about one specific thing. When you have your answer, the prototype has served its purpose. Discard it.

Consider the kinds of questions a prototype can answer:

  • Would this workflow make sense to a user?
  • Is this interaction intuitive?
  • Does this architecture feel maintainable as it grows?
  • Is this level of abstraction appropriate for the problem?
  • Can this concept be explained simply enough to fit on one screen?

None of these questions requires a production system to answer. A paper sketch, a few static screens wired together, or a script that exercises a single path through the logic will often surface the answer faster than weeks of design discussion.

The discipline is to articulate the question before building anything. If you cannot state what you are trying to learn, you are not prototyping — you are just coding without a specification. That can be fine too, but it is a different activity with different expectations.

Stating the question upfront also makes it obvious when you are done. The prototype succeeds when you have an answer, not when it is polished. The moment you learn what you needed to learn, stop. Write down the conclusion and move on.

This is liberating. It means most prototypes should be thrown away. That is not a waste — it is the process working as intended.
